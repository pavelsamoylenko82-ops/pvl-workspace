# autopilot-ops - безопасный автопилот, деплой, откат и отладка

Применяется, когда ИИ работает самостоятельно: собирает и проверяет проект, делает preview, выкладывает на сервер, чинит падения, ведёт ночную смену. Главный принцип: максимум автономности в безопасных действиях и жёсткий стоп там, где есть деньги, доступы, чужие данные или необратимость.

## 1. Матрица прав

| Уровень | Можно без спроса | Примеры | Граница |
|---|---|---|---|
| 1. Сам | Сборка, тесты, скриншоты, preview-деплой, проверки, запись в память | `npm run build`, pytest, локальный сервер, preview на Vercel, проверка 404, запись решения в `ПАМЯТЬ.md`, коммит в рабочую ветку | Не трогать боевые данные и чужие аккаунты |
| 2. Только после «да» | Боевой домен, кнопки «Сохранить/Подтвердить» в браузере, DNS/VPS, удаление с предварительным бэкапом, платные API-вызовы с оценкой цены | Пуш в main с автодеплоем, правка DNS, перезапуск сервиса на VPS, `rm`, платный запрос к API, публикация поста | Одно «да» = одно действие. Перед действием назвать цену, риск и план отката |
| 3. Никогда | Пароли/SMS, оплаты, создание аккаунтов, отправка сообщений клиентам, сетевые настройки ПК | Ввод пароля или кода из SMS, оплата подписки, регистрация нового кабинета, письмо/сообщение клиенту, смена Wi-Fi/прокси на компьютере | Только человек. Если секрет попал в чат или Git - сразу сказать о ротации |

Правила по умолчанию: сомневаешься - считай уровень 2 или 3. Разрешение не переносится на похожие действия. Удаление всегда после бэкапа и с явным списком файлов. Платный вызов - только с оценкой цены и лимитом.

## 2. Протокол `СХЕМА.md`

В каждом проекте в корне лежит `СХЕМА.md` на 1 страницу. Её читают перед деплоем, отладкой и ночной сменой. Обновлять при любом изменении инфраструктуры.

Шаблон:

```markdown
# СХЕМА: [проект]

Дата обновления:
Статус: [локально / preview / боевой]

## Части проекта
| Часть | Где живёт | Адрес/путь | Кто платит | Доступ |
|---|---|---|---|---|
| Сайт | VPS / Vercel | https://... | клиент / я | кто и как заходит |
| API / ИИ-консультант | VPS | /api/... | клиент / я | сервисный аккаунт |
| База | VPS | PostgreSQL/SQLite | клиент / я | бэкап, доступ |

## Ключи (только имена, без значений)
| Переменная | Назначение | Где хранится | Кто владелец |
|---|---|---|---|
| DEEPSEEK_API_KEY | ИИ-консультант | .env на сервере | клиент / я |
| TG_BOT_TOKEN | заявки в Telegram | .env на сервере | клиент / я |

## Поведение при падении
- Что видит клиент:
- Fallback формы/чата:
- Кто получает алерт:

## Мониторинг
- URL проверки:
- healthz ИИ-консультанта:
- Расписание cron:
- Куда алерт:

## Точка отказа
- Главная точка отказа:
- Почему:
- План на случай отказа:
```

Запрещено вписывать в схему значения ключей, пароли, коды и полные строки подключения. Только имя переменной, назначение, место хранения и владелец.

## 3. Git и выход из цикла («Стоп на 3-й попытке»)

- Коммит после каждого рабочего шага. Маленький diff, понятное сообщение, рабочее состояние.
- Перед откатом создать ветку `rollback/<дата-причина>` или зафиксировать известный хороший коммит. Не переписывать историю на боевой ветке без нужды.
- Не склеивать тесты и деплой в одну команду. Сначала тест, проверить exit code, только потом деплой. Ненулевой exit code = стоп, а не «наверное, прошло».
- В PowerShell проверять `$LASTEXITCODE`, в bash - `$?`. Пример: `команда; if ($LASTEXITCODE -ne 0) { Write-Error "стоп"; exit 1 }`.
- Логи и вывод команд сохранять в отчёт. Не печатать секреты даже в логах.

Алгоритм при зацикливании:

1. Остановиться после 3-й неудачной попытки починить один и тот же баг.
2. Откатиться на последний рабочий коммит/ветку.
3. Оставить ровно 1 команду воспроизведения ошибки.
4. Выписать 5 гипотез, включая не-кодовые:
   - путь/права/опечатка в имени файла;
   - не оплачен VPS или истёк срок;
   - нулевой баланс API;
   - geo-блок или 403;
   - кэш/CDN/старый service worker;
   - VPN/прокси/DNS.
5. Проверять гипотезы по одной, фиксировать вывод. Фикс только после подтверждения причин выводом, а не догадкой.

Если после подтверждённой причины фикс снова не работает 3 раза - стоп, откат и вопрос человеку. Не менять наугад конфиги, не переустанавливать всё подряд.

## 4. Безопасность и деплой

### Перед деплоем
- Показать список файлов, которые уходят на сервер. Выкладывать только папку сайта, не корень репозитория.
- Проверить `.env`/секреты: их не должно быть в списке.
- Проверить сборку и тесты, exit code каждого шага.
- Сделать бэкап текущей версии и БД, если меняется схема данных.

### Preview
- Открыть preview в режиме инкогнито, без авторизации и старых куки.
- Проверить мобильный вид, формы, консоль браузера, 404, редиректы.
- Только после успешного preview - боевой домен и только после «да».

### Ротация ключей
Порядок строго такой:
1. Прописать новый ключ в окружении/секрет-хранилище.
2. Перевыложить сервис и перезапустить его.
3. Проверить работу (healthz, реальный запрос, логи без ошибок).
4. Удалить старый ключ в кабинете провайдера.

Никогда не печатать значения секретов в чат, логи, скриншоты, коммиты и отчёты. В отчётах писать только имя переменной и статус «задан/не задан». Если секрет попал в Git - считать его скомпрометированным, отозвать и пересоздать.

### Обязательные проверки после выкладки
- `GET /.env`, `/server.js`, `/.git/config`, `/config.json` должны отдавать 404, а не содержимое.
- Боевые страницы не должны отдавать `X-Robots-Tag: noindex`.
- SSL валиден, редиректы с http на https работают.
- Формы реально отправляют заявку в нужный Telegram/чат.
- ИИ-консультант: лимит запросов на IP/сессию, ограничение длины и токенов, таймаут, CORS только для своих доменов, системный промпт без секретов.
- Ночные бэкапы БД включены, файл бэкапа защищён, восстановление проверено на тестовой копии. Без теста восстановления бэкап не считается рабочим.
- Скриншоты в эмуляции устройства: 320, 360, 390 и 1440 px.
- Проверка с мобильного интернета без VPN: сайт, форма, чат, скорость.

### Откат
- Знать заранее предыдущий рабочий артефакт/коммит.
- Откат БД делать только по плану миграции: сначала совместимость, потом код.
- После отката проверить healthz, главную, форму и логи.

## 5. Ночная смена

- Одна большая задача за ночь, а не десять мелких.
- В начале создать `НОЧЬ-YYYY-MM-DD.md`: цель, план, ограничения, что нельзя трогать.
- Пошаговый лог: время, действие, команда, результат, следующий шаг.
- На blocker - максимум 20 минут. Дальше зафиксировать в лог и перейти к другой части или остановиться.
- Вести список «Утром спросить»: вопросы, решения, которые требуют человека, и цена каждого варианта.
- Утром выдать короткий отчёт: что сделано, что проверено, что не получилось, что нужно от человека.
